# 2026-10-11 — M5: memory the guest frees goes back to macOS

## What landed

- `vmuc-hv`: handle-free stage-2 unmap/remap; the **stage-2 release
  matrix** probe; the **reclaim stall** probe; a fix for `align_inward`,
  which underflowed for ranges inside one host page.
- `vmuc-vmm`: the `Reclaimer` (inward alignment, `mincore` skip, unmap →
  `mmap(MAP_FIXED)` → map, one retry, a hole stops the VM, a gate closed
  before `hv_vm_destroy`, counters and a latency histogram);
  `VmBuilder::add_balloon`; vCPUs retry aborts on RAM addresses instead of
  emulating MMIO; the kernel image is mapped, not read.
- `vmuc-virtio`: virtio-balloon with free page reporting, inflate/deflate
  and the stats queue.
- `vmuc`: `vmuc stat [--watch] [--json]`, `vmuc reclaim`, `vmm.sock`
  `stat` / `reclaim_now` / `balloon_target`, a host-pressure responder
  (warn: drop caches and compact; critical with `pressureBalloon`: the
  plan's conservative balloon rule), reporting from order 5.

## Numbers (M4 Pro, Ubuntu 24.04, 4 vCPUs, 4 GiB)

| Target (plan M5) | Result |
|---|---|
| ≥ 90 % of freed memory back within 10 s | 96–100 % of a freed 2 GiB (`tests/bench/mem-reclaim`), e2e 90 % of 1 GiB in 6.2 s |
| idle Ubuntu footprint < 350 MiB after first reclaim | **not met: ~490 MiB**; ~240 MiB is Ubuntu itself and ~95 MiB the guest kernel's reservations for a 4 GiB ceiling |
| no reclaim-induced vCPU stall > 5 ms | host side: worst gap +13 µs at ~140k releases/s; in-guest 4–5 ms gaps during a 2 GiB free are the guest's own truncate/reporting work |
| release cost | p50 25–50 µs per range |

## Findings

1. **`phys_footprint` can lie.** A bare `hv_vm_unmap` + `hv_vm_map`
   drops it by the whole range while every page keeps its data; the
   drop vanishes when the host touches the pages. Only the full
   unmap/refresh/remap sequence really frees, and the probe now checks the
   data, not just the number (`2026-10-11-stage2-release-matrix.md`).
2. **Report from order 5, not 9**: same bulk-path speed, ~220 MiB less at
   idle (`2026-10-11-reporting-order.md`).
3. macOS's allocator keeps large freed blocks dirty and billed, and
   `malloc_zone_pressure_relief` does not give them back; the 31 MiB
   kernel image is now a read-only file mapping.
4. `footprint(1)` undercounts a VMM (it misses pages held through
   stage 2); vmuc reports `ri_phys_footprint`, which Activity Monitor and
   jetsam use.
