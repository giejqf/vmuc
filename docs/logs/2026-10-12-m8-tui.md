# 2026-10-12 — M8: TUI

## What landed

- `vmuc-tui`: a `Source` trait (instances with live status, memory
  accounting and forwards; console tail; actions; background notices),
  two minutes of samples per instance with derived host CPU load and
  release rate, screen state with the selection kept by name, and the
  screen itself: instance table, details (footprint sparkline scaled to
  the VM's memory, guest-memory gauge, released memory and its rate,
  forwards, errors), console tail with escapes and spinners cleaned up,
  key hints. Tests render into ratatui's `TestBackend`.
- `vmuc tui` in the binary: data from instance directories and control
  sockets (500 ms deadline per request), start and stop as background
  `vmuc` runs, reclaim as a control request, shell in the foreground.
- `Stat.host_cpu_nanos` (was the never-filled `vcpu_exec_nanos`): the
  VMM process's user + system time; `vmuc stat` prints it.

## Verified on HV (M4 Pro, macOS 26.6.2)

Run in a pty under `script(1)` against the `ubuntu` instance: the list
shows live numbers (0.4% host CPU for an idle Ubuntu guest, footprint,
guest used, release p50); `x` stops and `s` starts it with notices
("stopped ubuntu (0.5 s)", "ubuntu is running (3.4 s)"); Enter opens a
shell and returns to the TUI; `r` asks the guest to drop caches; `q`
quits. Watching costs 0.04 s of CPU over 10 s.

## Findings

1. "vCPU load" in the plan became host CPU load: the VMM process's CPU
   time covers vCPUs and device threads, which is what the VM costs the
   Mac, and needs no per-vCPU-thread call. `proc_pid_rusage` reports
   times in Mach ticks on Apple silicon; `getrusage` does not.
2. ratatui's `Terminal::clear` asks the terminal for the cursor position
   and errors when nothing answers (as under `script`); after a shell the
   TUI clears through the backend instead.
3. The control client's 30 s read timeout is right for `vmuc stop` and
   wrong for a once-a-second refresh; the TUI uses its own deadline.
