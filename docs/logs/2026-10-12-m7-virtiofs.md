# 2026-10-12 — M7: virtiofs

## What landed

- `vmuc-fs`: the FUSE 7.38 wire format with the Linux ABI translated on
  a Darwin host (errno, open flags, stat, dirents); an inode table keyed
  by host `(dev, ino)` with lookup counts and subtree renames; a
  passthrough backend that cannot leave the share (no symlink in any
  component, `.`/`..`/`/` refused in names, EROFS on read-only shares);
  request dispatch for the opcodes Linux sends in practice.
- `vmuc-virtio`: a virtio-fs device per share (tag in config space,
  high-priority queue plus one request queue). Requests run on a pool of
  four threads that never touch guest memory.
- `vmuc`: each configured mount becomes a device; the seed lists only the
  shares that were attached; a missing host directory is a warning.
  `stop --force` now kills a VMM that cannot finish tearing down.
- `tests/bench/fs` and `docs/benchmarks/fs.md`; the lifecycle e2e test
  checks a writable share both ways and the read-only `~`.

## Verified on HV (M4 Pro, macOS 26.6.2)

| What | Result |
|---|---|
| default `~` share | lists, reads, refuses writes (EROFS) |
| writable share | create, rename, symlink, hard link, chmod, truncate, sparse write, ENOTEMPTY; 64 MiB random file checksum matches on the host |
| a pool thread blocked in the host (FIFO with no writer) | other requests answered in ~1 ms meanwhile; `stop` completes |
| building from a shared tree | `rustc` run from the share (its shared libraries mmapped over virtiofs) compiles and links a static binary from source on the share in 0.16 s; `python3 -m compileall` over 570 files in 0.5 s; `git status`/`log` on this repo through the `~` share match the host |
| e2e `lifecycle` with a share | passes |

Numbers (`docs/benchmarks/fs.md`): 3.2 GB/s sequential write, 3.6 GB/s
cold read, open+close 72 µs (native macOS: 9.6 µs).

## Not verified here

- VZ virtiofs on the same host, the target: Lima is not installed.
- A full `cargo build` inside the guest: build scripts need a C linker,
  and installing one needs guest networking (the vmnet helper, root).
- Mounting the server through `/dev/fuse` on Linux, as the plan suggests:
  this session had only the Mac; the server is tested with request bytes.

## Findings

1. **macOS privacy prompts block host calls.** `getxattr` (and reading)
   under `~/Desktop`, `~/Documents`, `~/Downloads` waits until the user
   answers a TCC prompt, indefinitely. With one request thread the whole
   share froze, and so did device reset and VM teardown, leaving a VMM
   that not even `stop --force` could end. Requests now run on a pool,
   the worker never makes host calls, and `stop --force` falls back to
   SIGKILL. A guest touching a protected folder still waits for the
   prompt (as with Lima).
2. **Extended attributes are off by default** (ENOSYS once, then the
   kernel stops asking): Linux asks for `security.capability` before
   every write and for ACLs on every `ls -l` entry.
3. **Round trips, not host work, dominate small-file latency.** A guest
   open+close was OPEN, FLUSH and RELEASE, three synchronous trips of
   ~30 µs each. FLUSH now answers ENOSYS (110 → 80 µs) and opens and
   lookups are one syscall with `O_NOFOLLOW_ANY` /
   `AT_SYMLINK_NOFOLLOW_ANY` (→ 72 µs). The trip itself is half our
   wake-up and interrupt path, half guest kernel
   (`docs/experiments/2026-10-12-virtio-round-trip.md`).
4. **macOS refuses `O_NOFOLLOW | O_NOFOLLOW_ANY` with EINVAL.** Git opens
   `.gitignore` with `O_NOFOLLOW`; found by running git on the share.
5. **Linux's virtiofs driver never sends FUSE_INTERRUPT**, so a guest
   process blocked on a host call dies only by SIGKILL; a guest shutdown
   with one waits for systemd's stop timeout (30 s observed).
6. Ownership is passed through: the host's gid 20 (`staff`) shows as
   `dialout` in Ubuntu, as under Lima's VZ virtiofs. The guest user's uid
   matches the host's (501), so permissions behave.
