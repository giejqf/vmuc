# 2026-10-11 — M6: networking (vmnet path built, not yet run with root)

## What landed

- `vmuc-virtio`: virtio-net over a `SOCK_DGRAM` socket, one frame per
  datagram: zero-copy transmit, mergeable receive buffers, frames left in
  the kernel socket while the guest has no buffers. The mio waker
  doorbell is shared with vsock.
- `vmuc-net`: `vmuc-vmnet-helper` (root, accepts exactly `--mode shared`
  or `--mode bridged --interface NAME`, relays frames, parses nothing
  else), hand-written vmnet/xpc/libdispatch/blocks bindings, and the
  VMM-side launcher (`sudo -n`, socketpair on stdin, root-ownership check
  of the helper and every directory above it, sudoers rule).
- `vmuc`: the NIC when the helper starts, otherwise a warning event;
  `vmuc sudoers`; guest addresses in `vmuc list` and `status`; **port
  forwarding over vsock** (agent `sockets_watch` → host loopback
  listeners → agent tunnels), no NIC or root needed.

## Verified on this Mac

| What | How | Result |
|---|---|---|
| virtio-net data path in a real Linux guest | e2e `net`: busybox guest pings a peer the test plays on the socket's other end | ARP + 3/3 echo replies |
| the blocks ABI and vmnet bindings | helper run unprivileged | vmnet calls our completion block with status 1001 in 0.48 s |
| unprivileged vmnet on macOS 26 | probe of `vmnet_start_interface` and the new `vmnet_network_create` | both fail (1001, 1002): root is still required |
| missing helper or rule | `vmuc start` | boots without a NIC, prints why |
| port forwarding | e2e `lifecycle`: guest `python3 -m http.server` | reachable on host 127.0.0.1 in ~2 s |

## Not verified here

The vmnet path itself (helper as root, DHCP from vmnet, `curl` from the
guest, `ssh user@<guest-ip>`, `bench/net-iperf`) needs the helper
installed root-owned and the sudoers rule (`vmuc sudoers`), which this
session cannot do without a password. Until that runs, "networking works"
means "unit- and e2e-tested up to the socket, not yet run against vmnet".

## Findings

1. macOS 26's new `vmnet_network_*` API does not lift the root
   requirement for an ad-hoc signed process.
2. A sudoers rule must never name a user-writable binary; Homebrew's
   prefix is user-owned, so the helper is installed separately (Lima does
   the same for socket_vmnet), and vmuc refuses a helper anyone but root
   could replace.
3. A datagram socket gives no EOF when its peer exits, so the launcher
   watches the sudo child while waiting for the helper's hello.
4. Lima's catch-all must not mirror every loopback alias: forwarding
   systemd-resolved's 127.0.0.53:53 tried to bind host port 53.
