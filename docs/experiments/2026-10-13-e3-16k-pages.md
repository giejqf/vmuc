# 2026-10-13 — E3: 16 KiB guest pages

**Question.** vmuc's guest kernel uses 4 KiB pages (plan.md's locked
"Guest page size", for distro userspace compatibility) on a host whose
pages are 16 KiB. A 16 KiB guest would match the host: a quarter of the
struct pages, no 16 KiB host page held by one 4 KiB guest page, fewer
TLB entries. What does it change for memory and speed, and how much
userspace breaks?

**Method.** The guest kernel built with `CONFIG_ARM64_16K_PAGES=y` (the
rest of `vmuc.config` unchanged; built in a vmuc instance, sha256
`b7046fd6fd58…`) against the CI kernel (`2e58607f2620…`), each on a
fresh Ubuntu 24.04 instance from the template first booted on its own
kernel (4 vCPUs, 4 GiB), selected with `VMUC_KERNEL`:

- `tests/bench/mem-idle/run.sh` ×3, the 16 KiB kernel at the default
  reporting order (5: 512 KiB blocks) and at order 3 (128 KiB, the
  release granule); `tests/bench/mem-reclaim/run.sh` ×2;
  `tests/bench/boot-ssh/run.sh` ×5; `tests/bench/idle-cpu/run.sh` ×2;
  `tests/bench/mem-pressure/run.sh NAME build normal` ×2 (vmuc's kernel
  built with `-j4`: a CPU and memory workload).
- `tests/bench/pagesize/survey.sh` as root on both: packages, compilers
  and runtimes, Ubuntu's own services, and popular container images, one
  `ok` or `FAIL` line each.

M4 Pro, macOS 26.6.2.

**Result.**

| | 4 KiB | 16 KiB |
|---|---|---|
| Idle after three reclaims (mem-idle, median of 3) | **265 MiB** (runs 259–288) | 347 MiB at reporting order 5 (512 KiB); 301 MiB at order 3 (128 KiB; runs 288–343) |
| Guest MemTotal − MemFree at idle | 187 MiB | 247–251 MiB |
| 90 % of a freed 2 GiB back (mem-reclaim) | 0.5–2.1 s | 0.5–1.0 s |
| Idle right after reclaim (mem-reclaim) | 265–278 MiB | 332–340 MiB |
| Start to ssh, median of 5 | 2.59 s | 2.47 s |
| Idle CPU | 0.23 % | 0.17–0.20 % |
| Kernel build, `-j4`, two runs | 171 s, 171 s | **153 s, 152 s (−11 %)** |
| Footprint during the build, mean | 1159–1377 MiB | 1254–1480 MiB (+8 %) |
| Compatibility survey, 33 items | all ok | **all ok** |

The survey covered apt, Python with numpy, gcc, Node.js, Go, git, snap,
Ubuntu's Redis and PostgreSQL (started and queried), Docker, and 19
images, including the usual 16 KiB casualties: Redis (jemalloc, started
and pinged), MongoDB 7 (tcmalloc; started, a document inserted),
ClickHouse (jemalloc; a query run), Envoy, etcd (bbolt), Deno and Bun (JIT
engines) and uv. Nothing failed that did not also fail on 4 KiB.

The memory goes the other way from the hypothesis. The 16 KiB guest
saves 48 MiB of struct pages for 4 GiB and no longer pins host pages
with 4 KiB ones, but every page table, every cached small file and every
process's private mappings now round up to 16 KiB: the guest itself
uses 60–64 MiB more at idle, and reporting at the default order (512 KiB
blocks) leaves more behind. One interaction: `resize2fs` rounds a
filesystem's size down to whole pages, so a root filesystem grown under
4 KiB looks like a shrink under 16 KiB, and cloud-init's resize fails
(harmlessly, the filesystem is already full size) on every boot of an
instance switched from one to the other.

**Verdict.**

1. 16 KiB guest pages trade memory for speed: about 11 % faster on a
   CPU- and memory-heavy workload, slightly faster boot and lower idle
   CPU, for 36–82 MiB more at idle (14–31 %) and 8 % more under load.
   With memory the product, that is not a tie: the guest stays at
   4 KiB pages and plan.md's locked decision stands.
2. Compatibility was not the obstacle the decision assumed: nothing in
   the survey broke, the known-risky allocators included. If the speed
   is wanted, a 16 KiB kernel could be offered as an opt-in through
   `images[].kernel` (with `page_reporting.page_reporting_order=3` on its
   command line) without code changes; publishing it would need its own
   CI build.
3. The kernel for this entry is `vmuc.config` with
   `CONFIG_ARM64_4K_PAGES` replaced by `CONFIG_ARM64_16K_PAGES=y`, built
   with `guest/kernel/build.sh`; it is not shipped.
